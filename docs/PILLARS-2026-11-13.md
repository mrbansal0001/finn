# FINN by pillar: Push, Pull, Network

How each part works behind the scenes, how it reaches the screen, and who can see what. Written 13 Nov 2026 from the code and the live data (worker cycle of 01:34 IST). Numbers are what the system holds at that moment, not targets.

## 0. The machine underneath all three

```
 NSE / BSE public files ──► WORKER (Python, the owner's Mac, every 15 min) ──► SQLite (data/finn.sqlite)
 (feeds, PDFs, XBRL,             │ rules first, model only to read documents      │
  bhavcopy, transcripts)         │ (Gemini free tier first, OpenAI fallback)      ▼
                                 └──────────────────────────────────────► snapshot.json + 53 ledger files
                                                                                   │ sync (every cycle)
                                                                                   ▼
                                    SUPABASE: public tables (snapshot, ledgers, universe)
                                              private tables (contacts per visitor, RLS)
                                              demo template + checked function (network lines)
                                                                                   │
                                                                                   ▼
                                    WEB APP (Next.js on Vercel, Mumbai): reads, applies the visitor's
                                    rules, renders. It computes nothing that needs a model.
```

**One worker cycle (launchd, `StartInterval 900`, runs at login):**

1. `announcements`: whole-market RSS (about one day, ~600 items) → new filings stored.
2. `results_xbrl`: the results feed (exact P&L figures, rupee-precise).
3. `backfill`, once a day: 30 days of announcements for each holding, one request per company.
4. `read_filings`: up to 12 filings per cycle that rules can't summarise go to a model.
5. `requests_in`, `coverage_queue`, `requests_out`: visitors' ledger requests come down, at most two are built, statuses go back up.
6. `export`: builds the snapshot, including the network lines, which are computed locally.
7. `sync`: pushes the snapshot, ledgers, demo network and universe to Supabase.

The last cycle took about 15 seconds. Each step fails on its own without stopping the others, and the snapshot records when each step last succeeded (`freshness.worker_last_ok`).

**Hard dependency:** the worker runs on the owner's Mac. When the Mac is asleep, nothing new is read; the site keeps serving the last snapshot and says how old it is. GitHub Actions was blocked by a billing issue, so there is no cloud fallback.

**Rules that hold across all three pillars:**
- Exchange access controls are respected: no header spoofing, no proxies, no retrying after a refusal.
- Contact data never goes to any model.
- Model spend is capped in code (OpenAI $2.87 of $4 so far, 879 calls; Gemini 1,017 calls at $0).
- Every model response is cached, so rebuilds are free.

## 1. PUSH: what changed in the portfolio, and what counts as unusual

**The brief:** relevant changes in a mock portfolio, with configurable end-of-day alerts.

### Behind the scenes

| Stage | What happens | Where |
|---|---|---|
| Collect | RSS every 15 min; daily 30-day backfill per holding; results XBRL feed | `ingest.py`, `feeds.py` |
| Classify | NSE's own subject line → 17 categories by rules (written against 5,756 real filings); a tier is assigned: lead (can headline), notable (worth a look), routine (folded) | `classify.py` |
| Read | What rules can't summarise goes to a model: multi-label events from the first pages, or a bio annexure. Code enforces the copy: headline = verb + fact; a "why" is dropped unless it holds a number | `reader.py` |
| Results | The model only transcribes the P&L table; code checks the arithmetic identities and matches XBRL line by line; code computes QoQ, YoY, margins in bp and PBT before one-offs. A table that fails its checks is never shown | `results.py`, `xbrl.py` |
| Prices | NSE's daily bhavcopy (all stocks, one zip), cached forever. Every session that moved ≥1% or ≥1.2× its own 20-session average becomes a "move card" with a durable id; 30 sessions of history per holding for the charts | `prices.py` |
| Rank | Score = tier + kind + 4 × holding weight − age × 0.15. A move "leads" only at ≥5% with no material filing between the previous close and this one | `cards.py` |
| Edition | Four windows (24h, 3d, 7d, 30d): leads (max 3), more, routine counts and items. Routine XBRL-only filings are shown as plain-words facts, not raw XML | `cards.py`, `export.py`, `xbrl_facts.py` |

**Today (30-day window):**
- 248 filings became 105 cards plus 129 routine filings.
- 245 recorded sessions; 39 checked results tables.
- Headlines: 61 written by a model reading the document, 44 by rules.
- 14 of the 105 cards are "unclassified", the largest classification gap.

### In the app

- **The rules are the visitor's own.** Price and volume thresholds, muted categories and the number of leads live in a cookie (`finn_prefs`). The app applies them to the full set of moves the worker exported (everything at ≥1% / 1.2×), then groups them by company. Changing a rule needs no new worker run.
- **Edition (home):**
  - window control, then a one-line summary;
  - "Alerts at the close": the latest session's matches, at most three rows, each with a 20-session sparkline; the rest folded;
  - lead cards (growth bars for results, a sparkline for moves, one person, Investigate);
  - "Worth a look", "Routine, folded" and the end of the edition.
- **Card page:**
  - headline, the "why", and a chart (results Growth/Margins, or the 30-session price-volume chart with filing markers);
  - the question it raises, who can explain it;
  - the exact figures (folded);
  - "About this item": sources, ranking reasons, the ranking arithmetic.
- **What counts (settings):** sliders with a live preview of how many alerts the rules would have produced, a scatter of recorded sessions, category switches, edition length and display options.
- **Listen:** the browser's own speech synthesis reads a script written on the server for the active window. Nothing is sent anywhere.
- **Since last visit:** a browser-only window from the last data time this device saw.

### Who sees what

| Viewer | Sees |
|---|---|
| Anyone, including crawlers | The full edition (all of it is public market data) |
| A visitor with a session | The same, plus their own rules (cookie) and the network lines on cards |
| The owner | Everything above, plus the worker logs and the local database |

### Limits worth knowing

- **"Push" is not pushed.** There is no notification, email or web push. Alerts appear when the edition is opened, and Settings says so. This is the largest gap between the brief's word and the product.
- **End of day only.** Prices come from the bhavcopy, published after the close; nothing is intraday.
- **Holdings only.** Moves and price history cover the 18 holdings; the 4 research names have no alerts or charts.
- **Freshness depends on the Mac** being awake, especially on weekday evenings when results land.
- **Rules are per browser**, not per account; another device starts from the defaults.
- **14 unclassified cards** in 30 days show the subject line, not a typed category.

## 2. PULL: research grounded in primary documents

**The brief:** company research from primary company documents (no broker, news or model memory), with promised versus delivered over four quarters especially valued, working beyond the demo companies.

### Behind the scenes

```
discover (Screener page → links to exchange-hosted transcript PDFs, latest 4 calls)
  → read pages (text, or image for scanned pages)
  → extract (model, one call per transcript: what was promised, by whom, page, figures stated as actuals)
  → verify every quote against its page (code; unverifiable statements dropped)
  → link statements across calls into promise threads (code; deterministic)
  → statuses per call (code): open, revised, silent, ended, delivered / partly / missed
  → tracking against filed results while the year runs (code)
  → annual report: locate the MD&A, model summarises "What they do" and segments with page citations
  → ledger JSON (53 today, 1,808 promises), synced to the public `ledgers` table
```

- **What the model may and may not do.** It only transcribes. It never judges hit or miss, never links statements across calls, and never computes.
- **When a promise counts as settled.** Code requires all of the following:
  - a management speaker;
  - the same period and metric;
  - comparable units;
  - the figure printed in the quote;
  - a later call;
  - no forward-looking wording.

  This is deliberately strict, so very few promises settle: across all ledgers, 9 delivered and 4 partly. The value shows up mostly as **revisions (66), promises that went silent (53) and periods that ended with no outcome stated (242)**. 1,430 promises are simply open.
- **Accuracy is measured, not assumed.** Linking is scored against a hand-checked gold set: BEL precision 0.88 / recall 0.70, Deepak Nitrite 0.75 / 0.67. BEL and Deepak also carry the hand-checked ledger as a reference the visitor can switch to.
- **Any ticker:**
  - the universe covers every NSE equity;
  - an uncovered company shows "Not covered yet" with a request button;
  - requests are capped at 5 per visitor and 50 a day for everyone;
  - the worker builds at most two per cycle and writes the status back (queued, building, ready, or unavailable with a reason).
- **Results** on company pages come from the same checked tables as Push (39 companies).

### In the app

- **Company page:**
  - header with price, a 20-session sparkline and filing marks; a sticky section nav;
  - "What they do" (annual-report sentences with page links, segment-share bars where the report states shares);
  - "Worth your attention" (up to three promise questions);
  - latest results (chart, question, exact table folded);
  - Promised vs delivered (status counts with drawn icons; Needs attention, All and History views; each promise expands into a call-by-call replay with the quote and page per call, a calendar lane for dates, first-vs-latest wording);
  - methodology and provenance folded; people who'd know; filings; "About this company".
- **Investigate**, which joins the three pillars:
  1. what changed (a chart);
  2. what to check next (the company's own words);
  3. who could help;
  4. keep following.

  The question is written from the figures by fixed rules, never by a model, and can be edited. Promise links carry the title, so a rebuilt ledger can't reopen a different promise.
- **Search dock:** any company name or ticker, multi-word names included.

### Who sees what

Ledgers, results and the universe are **public read** (row-level security allows anyone to select them). Who requested a company is not readable: only the symbol, time, status and detail columns are exposed. A visitor with a session can request a build; a crawler cannot.

### Limits worth knowing

- **Discovery leans on Screener.** The documents read are the exchange's own PDFs, but the list of which transcripts exist comes from Screener's page. If that page changes, discovery breaks; the primary-source claim still holds.
- **Coverage:** 53 ledgers (the Nifty 50 plus portfolio and research names). Five holdings or research names have none (ITC, Tata Chemicals, Ather, Shaily, Kokuyo Camlin). Building them costs model calls, free tier first.
- **Builds wait for the Mac.** A request made while it sleeps waits until it wakes.
- **Linking is imperfect** (recall ≈ 0.7). Some revisions are missed, and two wrong links were found and fixed by hand on 12 Nov (Dixon, Cochin Shipyard).
- **Promise ids are positional.** Mitigated by title-carrying links; a stable id derived from the content would be the real fix.
- **Hand-checked reference ledgers** have per-call quotes only on the first and latest calls.

## 3. NETWORK: the right person at the right moment

**The brief:** personal relationships embedded where they become useful, also queryable directly. Profiles may be realistic synthetic data, clearly disclosed.

### Behind the scenes

- **Data:** `config/network.json`: 29 synthetic contacts (career history with dates, functions and listed tickers, education, domains, city, interaction counts, reciprocity, rating, how met) and 8 introducer edges with their context ("Rhea mentored Tanvi at Titan").
- **Matching** (`network.py`): deterministic and local; contact data never reaches any model. The evidence level decides the wording:

| Level | Meaning | Words used |
|---|---|---|
| certain | Same person, or a recorded role at the company | "was Head of Strategy at Titan, 2014–21" |
| dates overlap | Same organisation at the same time as a person named in a filing | "worked together" |
| same organisation | Shared employer or school, dates not overlapping or unknown | "both ex-X" |
| second degree | Reachable through a strong contact's recorded edge | "through Rhea Kapoor" |

- **Tie strength** = 0.40 × recency + 0.25 × frequency + 0.20 × reciprocity + 0.15 × the investor's rating. The "shared background" term was removed (audit F11); the docstring in `network.py` is out of date on this.
- **Per card:** filing-named people are matched first (dates overlap beats same organisation), then people who know the company; at most three lines. Current employees are flagged as **insiders** (public information only) and never suggested for a price move.
- **Per company:** every contact with a recorded link, plus second-degree paths.
- **Per promise:** a "verifier", the best non-insider whose recorded role fits the promise's text (496 today).
- **Privacy path (Supabase):**
  - The public snapshot carries **no** network data; `sync.split` strips every line out.
  - A first visit creates an anonymous Supabase session, and a trigger copies the 29 contacts into that visitor's own rows (forced row-level security, read-only to the visitor).
  - Network lines are identical for every demo visitor, so since migration 004 they are read from one template through a checked function (`my_network_lines()`), callable only with a session.
  - Anonymous demo visitors and their copies are deleted after 14 days (pg_cron, 03:00 IST).
  - Crawlers and other sessionless clients get no network at all, and the app says "didn't load" rather than "you know no one".

### In the app

- **Embedded:**
  - an initial avatar and name on lead cards;
  - "Who can explain this" on card pages;
  - "People who'd know" on company pages;
  - a verifier inside each promise;
  - the Investigate people step: Execution, Demand, Money and Rules lenses matched on recorded roles; empty lenses are said, not offered.
- **Person page:**
  - how you reach them (only when someone introduces you);
  - "Has seen both" when a career spans two covered companies;
  - why talk to them now (up to five items);
  - a note draft (folded; filled from templates; copied, never sent);
  - career bars;
  - "About this profile" with the tie-strength arithmetic.
- **Queried directly:**
  - the search dock matches names, themes, employers, tickers and schools;
  - "who knows X" gets a direct answer (who, or plainly no one);
  - the holdings Coverage view shows the people count per company and a "Lack context" filter.

### Who sees what

| Viewer | Sees |
|---|---|
| Crawler, no session | No people anywhere ("didn't load") |
| A demo visitor | The synthetic network as their own, readable only by them; disclosed as synthetic on every page |
| A real user (designed, not built) | Their own imported contacts in the same per-user tables |
| Models | Never any contact data |

### Limits worth knowing

- **A small graph.** 29 contacts and 8 edges, so second-degree reach is thin. Five covered companies have no one ("Lack context" shows them).
- **No import flow.** Real contact import is described in the write-up, not built.
- **Matching is by recorded function and dates.** It can miss a good person with an unusual title, and the lens captions say "matched on recorded role".
- **Same network for every demo visitor.** That's correct for a demo, but personalisation can't be shown.
- **Followed questions and drafts live in one browser**, by design, and the app says so.

## 4. How the three meet

```
PUSH  a change (results, a move, a filing)                ─┐
PULL  the company's own words on it (promises, results)   ─┼─► INVESTIGATE: question → evidence → person → follow
NETWORK the person whose recorded role fits the question  ─┘
```

The joins are concrete. A results card links to the promises on the same metric. A move card links to the filings before it, plus open promises. A people card links to what that person promised on calls. Each of these opens a person matched to the question. Followed questions then watch Push for the kind of document they wait for (next results, next call, any filing, a date).

## 5. What this suggests for refinement

| Pillar | Most valuable next step | Why |
|---|---|---|
| Push | A real push: a daily email or web-push digest of "alerts at the close" and followed questions with new evidence | It's the brief's word, and today nothing leaves the app |
| Push | Cut the 14 unclassified cards (rules or a model pass) | They are the least useful cards in the edition |
| Push | Price history and alerts for research names | Research names currently have no market context |
| Pull | Build the 5 missing ledgers (free tier first) | Every holding would have the four-quarter view |
| Pull | Stable promise ids (a hash of company, metric and first quote) | Removes the positional-id risk at the root |
| Pull | A fallback way to discover transcripts that doesn't depend on Screener | Removes a single third-party point of failure |
| Network | Fill the five "Lack context" companies with a contact or an edge | Makes the coverage view's gap close visibly |
| Network | A contact-import mock flow (CSV → per-user rows) | Shows how a real investor's network would enter |
| All | A cloud worker (Actions or a small VM) once billing allows | Removes the Mac as the single point of freshness |
